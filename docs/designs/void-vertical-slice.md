## Problem Statement

Technology is mostly learned by reading about it. VOID makes it something you manipulate: parameterized, shareable, remixable experiments on one common engine, built openly so the community can add experiments and evolve the product. Goal: a product people genuinely love using, not a hackathon demo. No subscription or revenue optimisation at this stage.

## What Makes This Cool

The unit of VOID is a *state you can send to a friend*. A link reproduces the exact experiment, parameters and seed. Nothing else in this space joins the explanatory depth of Visualgo or TensorFlow Playground with the share-and-remix culture of Shadertoy or CodePen, on one engine, in the open.

## Constraints

- Open source (Apache-2.0 already in repo); core platform stays free and open.
- Anti-AI-slop rules and honesty rules from the master spec are hard gates: no fake stats, activity, AI output or empty destinations.
- Every milestone must be independently testable and deliver something functional.
- Solo maintainer capacity today: moderation and community features are expensive; gate them on evidence.
- Must grow without a rewrite: experiment contract, serialization and URLs are the stable surface.

## Premises (all agreed by owner, D2)

1. Wedge is depth + remixability, not breadth of 30+ modules.
2. The growth loop is a link that reproduces exact experiment state; it needs no backend or account.
3. Accounts, comments, moderation (spec M7–M8) start only after share links are demonstrably opened and remixed.
4. Homepage sections are backed by the real experiment registry; community-driven sections stay honest early states or are omitted (spec M2 conflict resolved).
5. The hero is itself a small working experiment, not decoration.
6. Open-source contribution is a product feature: manifest-per-folder experiment SDK and `CONTRIBUTING.md`.
7. Order: shell → engine + one experiment → homepage built alongside it (spec put homepage before engine).

## Approaches Considered

- **A: Vertical slice, engine-first (chosen).** Real thing at every milestone; homepage never fakes data.
- **B: Spec order, full stack up front (rejected).** Homepage would be fake/empty; heavy dependencies before any experiment needs them.
- **C: SDK-first, contribution-led (merged into A).** Its extension boundary is kept; its "no visible product early" cost is rejected.

## Recommended Approach

Approach A with C's contribution boundary. First vertical slice (owner's definition, D3):

1. A distinctive VOID homepage.
2. A working experiment registry.
3. One complete interactive experiment.
4. A reusable experiment interface.
5. Configuration serialization.
6. A working shareable experiment URL.

Candidate first experiment: **Algorithm Arena** (sorting + side-by-side comparison with operation counters). Reason: pure deterministic core, trivially unit-testable, real "whoa" from two algorithms racing on the same data, and it doubles as the homepage hero. To be confirmed in `/plan-eng-review` and `/plan-design-review`.

- Contribution path details (experiment folder layout, review checklist, license/CLA stance).

## Success Criteria

- A stranger opens a share link and sees the exact experiment state the sender saw (round-trip test in CI and a browser test).
- The first experiment's results are verified by automated tests against known-correct outputs.
- The homepage contains no number, name or activity that is not real or plainly labelled illustrative.
- Adding a second experiment requires touching only its own folder plus one registry line (proven by actually adding one).
- Accessibility and performance targets from spec §17–18 are *measured* and reported, not assumed.
